# Agent 安全，从"守大门"到"守管道"：一份分层防御清单

> 原文首发于微信公众号「Wenyan的呜哇」，2026-09-19。[阅读原文](https://mp.weixin.qq.com/s/d4Rp7BdZOL7GCKK3o8mTLQ)

> 本文围绕佛罗里达国际大学（FIU）团队发表在 arXiv 的 SoK 综述《Rethinking Jailbreaking in the Era of Agentic AI》（arXiv:2609.12413）展开。这篇论文系统梳理了 116 种攻击和 63 种防御，把过去主要围绕单轮对话的 Jailbreak 研究进一步扩展到完整的 Agent 执行管道，并通过系统实验揭示了当前 Agent 安全体系中的关键缺口。以下内容以论文的核心发现为基础，并进一步做一些面向实际 Agent 系统的工程化解读。

---

## 一、Agent 来了，但安全观念还停留在"聊天机器人"时代

过去一年，大模型领域最显著的变化之一，是系统从"对话助手"逐步走向"自主 Agent"。这些系统不再满足于回答问题，而是开始规划任务、调用工具、维护记忆、与其他 Agent 协作，独立完成多步骤的复杂操作。

能力边界扩张之后，安全问题也随之改变。传统的大模型安全研究，往往重点关注：如何防止用户通过精心构造的提示词，诱导模型输出有害内容。对应的防御思路也比较直观——在输入端过滤危险内容，在输出端检测有害文本，中间过程通常被视为黑盒。

但当 LLM 被包装成 Agent，它不再只是"说话"，而是开始"行动"。它可以读取文件、发送邮件、调用 API、修改数据库，甚至指挥其他 Agent 协同作业。

这意味着攻击者的目标也发生了变化：不一定要让模型一次性说出一句危险的话，而可能是通过影响 Agent 的规划、记忆、工具调用或协作过程，让它在多个步骤中逐步偏离原始目标。

因此，这篇 SoK 综述最值得关注的，并不是某一种新的攻击技巧，而是它重新拉长了我们观察安全问题的时间尺度：真正需要保护的，不只是 Agent 的输入和输出，还有从输入到行动的整条执行链。

## 二、先回答一个根本问题：到底是谁在攻击？

在深入讨论攻击面之前，有必要先厘清一个容易混淆的问题：这些安全威胁，是模型"自己"发起的吗？

对于本文讨论的越狱与对抗性威胁而言，攻击者通常并不是模型本身，而是利用不同的输入和信任边界，影响 Agent 后续执行。攻击入口在 Agent 场景下变得更加多元。

终端用户可能直接发送对抗性提示，例如通过 AutoDAN、PAIR 等自动化方法生成提示，要求 Agent 执行多步有害任务，或诱导 Agent 在规划中植入恶意逻辑。

内容供给方则可能通过污染网页、文档、数据库等内容，让 Agent 在检索或调用工具时被动摄入被污染的信息，进而影响后续决策。

工具或 API 的控制方可以在 Agent 调用外部服务时返回恶意构造的结果。Agent 如果将这些结果当作可信信息，就可能据此做出错误甚至危险的决策。

而在多 Agent 系统中，其他被攻破的 Agent 也可能成为攻击载体——一个受到攻击影响的 Agent，可以通过正常的协作消息，将恶意内容传播给其他 Agent，进一步扩大影响范围。

这里也需要区分一个近年来常被讨论的问题：Scheming（密谋/表里不一）。关于模型在特定条件下是否会表现出策略性欺骗行为，已有相关研究讨论，但这并不是本文的核心。对 Agent 防御而言，更直接的问题是：攻击者如何利用输入、外部内容、记忆、工具返回结果或 Agent 间通信，逐步改变系统的执行轨迹。

因此，防御重点不是假设模型会"突然叛变"，而是识别并控制那些可能改变 Agent 行为的信任边界。

## 三、攻击面从"一扇门"变成"一条管道"

传统 LLM 的主要攻击入口是用户输入。攻击者能直接控制的，通常就是发给模型的那段文字。

但 Agent 的执行是一条管道，攻击者可以尝试影响其中多个节点：

用户输入端：这是最传统的入口。Agent 时代的变化在于，攻击可以被拆成多个步骤，每一步单独看似乎都无害，但组合起来可能导向有害目标。

规划与推理端：Agent 会把用户请求分解成多个子任务。攻击者可以尝试影响这个分解过程，让 Agent 对原始意图产生偏离。例如，一个看似普通的整理任务，可能被诱导成包含不必要的删除、外发或越权操作的计划。

记忆端：Agent 拥有持久记忆，意味着一次交互产生的内容可能影响未来的会话。攻击者可以尝试向记忆中注入恶意指令，使污染与触发在时间上分离。今天写入，未来触发，会显著增加排查和溯源难度。

工具端：Agent 能调用外部工具，也就意味着工具返回的数据本身可能成为攻击载体。攻击者既可以操纵工具返回结果实施间接提示注入，也可能诱导 Agent 调用具有真实副作用的工具。

多 Agent 通信端：在多 Agent 系统中，一个受到攻击影响的 Agent 可以通过消息传播恶意内容。这样一来，原本局部的攻击就可能沿着协作链扩散。这里还容易出现一个误区：看起来像是 Agent A 在"攻击" Agent B，但从更完整的攻击链看，Agent A 本身也可能只是外部攻击的跳板。

所以，传统 LLM 的安全更像是"守一扇门"；Agent 的安全则更像是"守一条管道"。而且真正值得警惕的，是管道中的每一次状态转换都可能成为新的信任边界。

## 四、三个值得警惕的发现

论文的系统梳理和实验结果，可以归纳成三个非常值得关注的结论。

### 发现一：模型能拒绝恶意请求，不代表 Agent 难以被攻破

当前主流大模型经过安全对齐训练后，对于直白的恶意请求通常具备较强的拒答能力。

但论文强调："能够拒绝普通恶意请求"和"能够抵抗精心设计的对抗攻击"并不是同一个维度。AutoDAN、GCG、PAIR 等攻击方法，依然能够从不同角度寻找绕过安全对齐的路径。

更重要的是，在 Agent 场景下，攻击者并不一定需要一次性突破模型本身。只要能影响规划、记忆、工具调用等中间环节，就可能让 Agent 在执行过程中逐步偏离原始目标。

所以，模型本身的安全对齐很重要，但它解决不了全部问题。模型安全能力与系统安全能力，不应该被当作同一个概念。

### 发现二：防御效果高度依赖具体场景

论文在统一实验框架下测试了 16 种代表性防御手段，结果显示：不存在一个可以在所有模型、所有攻击和所有场景下都稳定占优的"银弹"。

同一种防御，在不同模型上的效果可能明显不同；一些方法虽然能够降低攻击成功率，却可能同时增加响应延迟，或者带来更严重的过度拒绝（Over-refusal）。

这意味着，Agent 安全不是"加一个护栏"这么简单，而是一个需要在安全、效用、效率之间持续权衡的工程问题。

论文中的实验结果更适合被理解为：防御方案需要经过具体场景下的测试和组合，而不是直接照搬某一个实验中的最佳结果。

### 发现三：最容易被忽视的盲区，是"最终输出安全，但中间已经发生了危险动作"

这是理解 Agent 安全最重要的一点。

举一个简化的假设场景：攻击者通过污染检索内容、注入记忆或操纵工具返回结果，让 Agent 在规划阶段决定执行一个危险操作。Agent 随后读取了敏感文件，又调用邮件工具把数据发了出去。但在最后生成回复时，输出层分类器检测到有害内容，将回复拦截成一句"抱歉，我无法完成这个请求"。

从用户侧看，Agent 拒绝了请求，似乎很安全；但从系统侧看，真正的副作用已经发生。最后的文字被拦截，并不能撤销前面已经执行的操作。

这就是所谓的中间层妥协：规划、记忆、工具调用等中间环节已经受到影响，而防御体系却仍然只盯着最终输出。

可以把它想象成一栋大楼：安保只在出口检查证件，但楼内的水管、电路和通风系统早已被动过手脚。出口查得再严，也无法替代对内部结构的控制。

> 真正需要关注的问题，不只是 Agent 最后说了什么，而是它在整个执行过程中做了什么、写了什么、调用了什么、访问了什么、传给了谁。

## 五、为什么只在输入和输出设卡不够？

传统的"输入过滤 + 输出检测"之所以在 Agent 时代显得不够，是因为它默认把中间过程当成黑盒。但对 Agent 来说，中间过程本身就可能产生副作用：规划会决定下一步行动，记忆会改变未来上下文，工具调用可能立即触发真实操作，Agent 间消息还可能继续传播污染。

因此，如果防御只设置在管道两端，中间发生的副作用可能已经无法靠输出过滤挽回。

这也是论文带来的一个重要理念转变：Agent 安全的评估单位，应该从"单次请求—响应"进一步转向"整个执行轨迹"。

换句话说，真正需要检查的不是某一条回复是否安全，而是从输入到行动的每一次状态转换是否都在安全边界之内。

## 六、怎么落地：三层防御 + 一个基础设施底座

下面这套框架不是论文原文提供的"一键部署方案"，而是基于论文对攻击面和防御效果的分析，进一步做的工程化拆解。

### 第一层：边界层——控制"什么能进来"

这是最基础的一层，包括用户身份认证、输入过滤、速率限制、租户隔离等，目标是尽可能降低明显恶意输入直接进入系统的概率。

但边界层主要处理显式入口，对通过检索内容、工具返回结果或记忆实现的间接注入并不充分。因此，它是必要的起点，但不能成为整个安全体系的终点。

### 第二层：管道层——控制"执行过程中每一步是否合规"

这是 Agent 安全设计中最容易被忽视、也最值得单独建立控制机制的一层。核心思想不是只检查 Agent"最后说了什么"，而是对关键状态转换设置控制闸门。

规划闸门：尽可能让 Agent 输出可校验的结构化计划，例如明确步骤、涉及的工具和访问的数据范围。执行前由独立机制检查计划是否符合安全策略，以及是否与用户原始意图一致。高风险计划可以进入人工审批。

记忆闸门：把 Agent 记忆视作需要治理的数据资产。写入前进行必要的内容审查，记录来源和时间等元数据，设置适当的过期策略，并严格隔离不同用户或租户的记忆。核心原则是：不能默认 Agent 自己生成的记忆天然可信。

工具闸门：对每个工具建立明确的权限和风险边界。调用时检查当前会话是否具备权限、参数是否在允许范围内，以及当前调用与之前行为组合后是否出现异常。涉及发送邮件、支付、删除等高风险动作时，可以设置更高等级的审批要求。

通信闸门：多 Agent 之间不应默认完全互信。可以通过可验证身份、消息完整性保护、有限范围的能力授权和通信审计等机制，降低攻击在协作链中的扩散风险。

### 第三层：模型层——控制模型本身的行为倾向

这一层包括选择具备较好安全能力的基座模型、通过系统提示强化安全约束、部署输出分类器，以及其他模型侧干预方法。

论文的实验结果提供了一个务实提醒：模型层防御的效果并不是无限叠加的，额外的安全收益需要结合延迟、过度拒绝和任务效用一起评估。

因此，比较合理的思路不是把所有安全压力都放到模型层，而是把模型层作为整个体系的一部分，与边界控制和执行过程控制配合起来。

### 基础设施层：兜底、隔离与溯源

除了上述三层，还需要一个基础设施底座：零信任网络、白名单访问、沙箱化执行、不可篡改的审计日志，以及 Human-in-the-Loop 网关等。

它们解决的是另一个问题：即使前面的模型和策略判断出现误差，也尽量限制错误行为的影响半径，并留下足够的信息用于事后溯源。

## 七、真正上线时，团队需要回答的几个问题

### 风险应该怎么分级？

并非所有 Agent 都需要同等强度的安全控制。一个只读查询内部文档的 Agent，和一个能够转账、发邮件、修改生产配置的 Agent，潜在损害完全不同。

因此，更实际的做法是结合潜在损害、权限范围和自主程度进行风险定级，再决定需要多强的防御和审批。

### "中间态"有没有真正受到保护？

相比"有没有加一个输出分类器"，上线前更应该回答下面 6 个问题：

1. 记忆谁能写？写入前有没有必要的审查、来源记录和隔离？
2. 工具谁能调用？权限和参数有没有明确边界？
3. 高风险动作谁批准？发送、支付、删除等操作是否需要更高等级控制？
4. Agent 之间是否默认互信？有没有身份、权限和通信审计？
5. 执行轨迹能不能完整审计？能否知道 Agent 为什么做出某一步，以及访问了什么？
6. 安全测试到底看什么？只看最终回复，还是同时检查规划、记忆、工具调用和其他中间态？

如果这些问题很多都没有明确答案，那么系统的安全边界往往还主要停留在"输入过滤 + 输出检测"，而没有真正延伸到 Agent 的执行过程。

### 还有三个常被忽视的运营问题

不要把"强模型"当成完整安全方案。更强的模型可以提高很多基础能力，但并不意味着整个 Agent 系统自动获得同等级别的安全性。随着记忆、工具和多 Agent 协作加入，安全边界也会同步增加。

安全、效用和效率必须一起测。一个防御措施降低了攻击成功率，却让正常请求大量被拒绝、延迟显著增加或成本明显上升，就不能只用"安全率"一个指标评价。论文实验也提醒我们，Agent 安全不是单指标优化，而是安全、效用、效率之间的多维权衡。

持续对抗测试，而不是一次性验收。攻击方法、工具链、记忆机制和协作关系都在变化，因此安全测试也应该持续进行，并重点观察中间态是否发生妥协。

---

## 八、结语

这篇 SoK 论文真正有价值的地方，不在于提出了某个具体的新算法，而在于它重新定义了 Agent 安全问题的观察范围。

当 LLM 变成 Agent，攻击者的目标就不再只是"让模型说错话"，而可能是影响规划、记忆、工具调用和 Agent 间通信，让系统在多个步骤中逐渐偏离原始目标。

这也意味着，Agent 安全设计需要从"给输入和输出各加一个过滤器"的思路，进一步转向对整个执行管道进行控制。

管道中的每一个转换点——规划、记忆、工具、通信——都可能成为新的信任边界，都需要相应的权限、校验和审计机制。

> 真正需要保护的，不只是 Agent 最终说了什么，而是它在整个执行过程中做了什么。

Agent 的自主性打开了巨大的想象空间，但自主性越强，系统就越不能只依赖模型本身来保证安全。
