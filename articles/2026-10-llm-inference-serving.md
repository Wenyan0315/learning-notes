# 大模型推理引擎演进：从持续批处理到以缓存为中心的调度

> 原发于微信公众号「Wenyan的呜哇」,2026-10-17
> 系列上一篇:[《大模型为什么一个字一个字地"蹦"?四篇论文讲清推理加速》](https://github.com/Wenyan0315/learning-notes/blob/main/articles/2026-10-llm-inference-optimization.md)

上一篇讲的是单条请求:为什么逐字生成、怎么算得更快、KV Cache 怎么省显存。这一篇换一个问题——你在用这个模型的那一刻,还有成千上万人同时在用。它是怎么同时扛住这么多人的?为什么高峰期会卡、会排队?

先把答案的轮廓给出来:同时服务一千个人,不需要一千份模型。一个模型实例里,权重可以供多条请求共享,每条请求则维护自己的上下文状态。推理引擎把一部分请求拼在一起计算,让写完的退出、新来的补位,暂时装不下的排队。流量更大时,还可以部署多个模型实例分担。真正的难点是:既想让机器多接活,又要把等待控制在可接受的范围内。

接下来按四个问题展开:请求怎么补位?长输入怎么少挡路?两个阶段怎么分工?算过的上下文怎么复用?对应的四篇论文是 Orca(OSDI 2022)、Sarathi-Serve(OSDI 2024)、DistServe(OSDI 2024)和 Mooncake(FAST 2025)。这是理解问题的顺序,实际系统往往会把这些方法组合起来用。

## 01|先看一条请求:模型回答时,机器在干什么

整条线索都建立在同一件事上:模型回答的固定节奏。用一条请求拆开看。

先交代一个单位:**token** 是模型处理文本的基本单位,由分词器切出来,可能是词的一部分、一个词或一个符号,不一定对应一个汉字。下面先看最常见的逐 token 生成方式:你输入 1000 个 token,模型的回答分两段产生。

```
(图里把 token 简化画成一个字,实际不一一对应)

输入: [大][模][型] … 共 1000 个 token
        │
        │ Prefill:处理输入(这里画的是不分块的情况)
        ├─ 蹦出第 1 个字「一」
        └─ 前文的计算结果存进缓存(KV Cache)

之后 Decode:一步一个字
   「一」→「种」→「神」→「经」…
   每步:利用前文缓存继续计算 → 算出下一个字
   (新字的结果也追加进缓存,缓存越来越长)
```

**Prefill(预填充)**,可以理解为“读题”:处理输入,产生第一个输出 token,同时把前文的计算结果存进缓存。输入 token 可以并行处理,也可以分块处理,后面会讲。

**Decode(解码)**,可以理解为“接着写”:每一步利用前文缓存继续计算,产生下一个 token。前后步骤有依赖,必须接着已有内容往下生成;不同请求之间则可以并行推进。

这个缓存就是 **KV Cache**。它省计算的方式很直接:把前文算过、后面还要用的结果留下来,不用每生成一个 token 就把全部历史重算一遍。代价是占空间:在这里讨论的常规缓存方式下,上下文越长、同时处理的请求越多,缓存就越大。生成时通常需要把用到的缓存放在 GPU 显存里,能同时容纳多少条请求,也会受到它的限制。

两段的工作方式不同。**Prefill 一次处理很多输入 token,通常能让 GPU 集中做大量计算;Decode 每条请求每步只推进一个 token,却仍要读取模型权重和上下文缓存,在小批量场景下,更容易受数据读取速度限制。**“算得够不够快”和“数据来不来得及送到”,是两种不同的瓶颈。

后面反复用到两个指标:

- **TTFT(首 token 延迟)**:从请求发出到第一个 token 返回,衡量“等多久开始回答”。包含排队和输入处理等时间,具体测量也可能从服务器收到请求时算起。
- **TPOT(平均每个输出 token 耗时)**:从首个 token 到最后一个 token 的时间,除以后续生成的 token 数,衡量“开始回答后,平均写得多快”。平均值也可能掩盖偶发的卡顿,要看输出是否平稳,还得观察相邻 token 的时间间隔。

一条请求的节奏就是这样。接下来把镜头拉远:一千条这样的请求同时来,怎么办?

## 02|先把多个人的请求拼起来算

单跑一个请求时,Decode 每轮只推进一个 token,往往用不满 GPU 的算力。提高机器利用率的一个关键办法,是把多条请求拼成一个 batch(批次)一起算。一次读取的模型权重可以用于多条请求的计算,但各条请求仍保留自己的上下文,不会把甲的问题接到乙的答案上。

先看一种简单做法——**静态批处理**:把一批请求固定下来,等整批结束再接下一批。问题是,有人只要一句话,有人要写一篇长文。前者已经结束,空出来的位置却不能马上接新请求,整批什么时候结束由最长的那条决定。拼批提高了利用率,固定的进出方式又浪费了一部分机会。

还有一个独立的限制:缓存怎么分配。输出最终多长事先不知道,一种简单办法是提前预留一大块连续空间,例如按允许的最大长度来留。但请求未必用得完,空着的空间又不能交给别人。vLLM 的 PagedAttention 论文在所评估的既有分配方案中观察到,用于 KV Cache 的空间只有约 20%–40% 真正在存储 token 的状态,其余被预留空间、碎片等占据。上一篇讲的分页管理,解决的正是这类浪费。

缓存管理先放在一边,这一篇重点看调度:请求一定要等整批结束才能补进来吗?

## 03|Orca:写完一个,就补进一个

Orca(OSDI 2022,首尔国立大学和 FriendliAI)的核心改动一句话能说完:**调度不再按"批"发生,而是按"每轮迭代"发生。**

Decode 本来就是一轮一轮跑的:每轮给 batch 里正在解码的请求各生成一个 token。Orca 让每一轮跑完都成为一次调度机会——写完的请求退出,有余量就接入排队的请求。这就是后来所说的 continuous batching(持续批处理),像一辆沿途上下客的车,不用等所有乘客都到站,才允许下一批人上车。

配套的“选择性批处理”则负责让这件事能高效执行:适合合并的计算一起做,需要分别处理各自上下文的注意力计算,在 Orca 的实现里按请求单独做。

效果:GPT-3 175B 上,相同延迟水平下,吞吐最高达到 NVIDIA FasterTransformer 的 36.9 倍。数字很大,但要看清前提——比较的是论文当时的系统配置,包含批处理和调度方式的差异,不能理解成一次模型计算快了 36.9 倍。

但“随时补位”不等于“补进来没有代价”。新请求要先做 Prefill,如果带来很长的输入,又一次性处理,就可能拖长已有请求这一轮的 Decode。用户的体感就是:字正往外蹦,突然停住了。新来的长请求越多,这种干扰就越值得处理。

## 04|Sarathi-Serve:长输入拆开处理,少挡别人的路

上一节末尾的矛盾是:新请求不进来,排队会拉长它的 TTFT;长请求一口气处理完,又容易让已有请求的 Decode 停下来等。

Sarathi-Serve(OSDI 2024,Georgia Tech 和微软)的解法是**分块预填充**(chunked prefill):把长输入拆成小块,分多轮处理。比如两万 token 的输入,可以拆成二十块,每块一千 token——这里只是示意,实际块大小要按每轮的预算来定。

关键不只是“切小”,还包括**先安排正在进行的 Decode,再用这一轮剩余的 token 预算处理 Prefill**。这样,旧请求不用停下来等新请求把长输入全部算完。这就是论文里的无停顿调度(stall-free scheduling):让输出持续推进,同时控制每轮工作量。

切块也有取舍。块越小,越容易控制每轮延迟;切得过碎,又可能降低计算效率、延长输入处理时间。所以它能缓解长 Prefill 造成的停顿,并不意味着任何负载下都不会卡。

效果以一个实验为例:Mistral-7B 单张 A100,满足论文所设延迟目标时,服务容量达到当时 vLLM 基线的 2.6 倍。

这里的 **SLO(服务等级目标)**,就是运营方给体验定的达标线。Sarathi-Serve 的实验重点约束输出间隔,例如要求 99% 的输出 token 间隔不超过指定上限,避免少数很慢的间隔被平均值掩盖。容量达到 2.6 倍,指在这样的要求下,能承接的请求速率达到基线的 2.6 倍。

这种方法已经进入实际引擎。例如 vLLM V1 会在支持的情况下默认启用 chunked prefill。

不过,拆成小块之后,Prefill 和 Decode 仍然共用 GPU。接下来可以再问一步:如果两个阶段各用一组资源,会不会更容易安排?

## 05|DistServe:读题和写答案,交给两组 GPU

DistServe(OSDI 2024,北京大学等)研究的是:在严格的延迟要求下,Prefill 和 Decode 放在同一组 GPU 上,如何避免顾此失彼。两个阶段适合的批大小、并行方式和资源配比往往不同,共用资源就难以分别调整。为了让两头都达标,系统可能不得不多配一些机器。

DistServe 的方案是拆开:**Prefill 和 Decode 部署到不同的 GPU 池**,各自调整并行策略和资源配比。负责 Prefill 的实例处理完输入,把 KV Cache 交给负责 Decode 的实例继续生成。两个阶段的英文首字母分别是 P 和 D,这就是常说的 **PD 分离**。

论文以 **goodput** 为优化目标。具体到这里,看的是:达到规定的延迟达标率时,每张 GPU 最多能承接多高的请求速率。例如要求至少 90% 的请求同时满足 TTFT 和 TPOT 限制,就测在这条要求下能接多少请求。这样既考核处理量,也考核服务质量。

论文报告,在其测试条件下,可承接请求速率最高达到比较系统的 7.4 倍。代价则是两个阶段要分别保有模型权重,还要传输 KV Cache,部署和调度也更复杂。DistServe 会结合网络带宽安排实例位置,控制这笔通信成本。最终要算的是:这些额外开销,能不能换来更高的每张 GPU 服务容量。

PD 分离也不是 DistServe 独有的方向,Splitwise 等工作同样研究过。是否值得拆开,要结合负载、延迟目标和通信条件判断。

顺着缓存往下看,还有一个机会:这些花了时间算出来的结果,能不能留给后续请求复用?输入越长,省掉重复计算就越有价值。

## 06|Mooncake:算过的上下文,尽量接着用

Mooncake(FAST 2025,月之暗面和清华大学)获得了那届最佳论文奖,也是 Kimi 的生产服务平台。按论文发表时的介绍,它已运行在数千节点上,每天处理超过 1000 亿 token。

它面对的现实是:上下文越长,Prefill 越贵;而后续请求常常包含已经处理过的前缀,例如同一段系统提示词、同一轮对话里不断增长的历史。假设你先让模型读一份长文档,随后连续追问,每次输入都从相同的文档内容开始,就有机会复用这部分缓存,只计算后面新增的内容。

这里的“相同”有条件:在模型和相关计算配置一致时,输入开头的 token 序列需要匹配。只是两段话意思相近,或者同一份文档前面换了一段提示词,都不能直接按相同前缀复用。

Mooncake 把这种复用纳入整个集群的安排:

- Prefill 和 Decode 分开部署;
- 利用现有 GPU 服务器上未充分使用的 CPU、内存和 SSD 等资源,组成**全局 KV Cache 池**,扩大可保留的缓存容量;
- 调度器**以缓存为中心**:不只看哪台 GPU 有空,还要看哪些缓存可以复用、搬过去要多久,再决定请求交给谁。

它还处理了一个高峰期的问题:如果预计后面的 Decode 已经接不住,就尽早拒绝部分请求,避免先花大量算力做完 Prefill,最后仍然无法按要求完成。这种基于预测的早期拒绝,也是调度的一部分。

按 FAST 2025 正式版论文,在 Kimi 实际部署中,A800 和 H800 集群相较之前的系统,分别多处理了 115% 和 107% 的请求。不同测试条件下的结果见文末;这些收益来自整套架构和调度设计,不能全部归到缓存复用一项上。

## 07|回头看:多接请求,也要让人等得住

| 方法 | 主要改善 | 仍需处理 |
|---|---|---|
| 静态批处理 | 多条请求一起算 | 空位不能及时补人 |
| Orca:迭代级调度 | 请求能及时退出、补位 | 长 Prefill 干扰 Decode |
| Sarathi-Serve:分块预填充 | 限制每轮的 Prefill 工作量 | 块大小与效率的取舍 |
| DistServe:PD 分离 | 两个阶段分别配置资源 | 缓存传输与资源配比 |
| Mooncake:围绕缓存调度 | 复用已有计算结果 | 缓存放哪、搬多远、保留多久 |

回到标题,一千个人同时提问,系统靠共享模型权重、把请求拼批、及时补位来提高利用率,再通过分块、阶段分工、缓存复用等方法减少等待和重复劳动。容量不够时,仍然需要排队、扩容或拒绝部分请求。

这些方法围绕同一个目标:**在有限资源下多服务一些人,同时让他们既不用等太久才开始看到回答,也不用在生成过程中频繁停下来。**TTFT 和输出速度描述体验,goodput 则把体验要求与服务容量放在一起衡量。

系统侧之外,模型结构也能减少缓存开销、加快生成。那是另一条线,留到下一篇单独讲。

最后留三个追问,下次看到推理引擎的宣传数字可以用:加速的是单条请求的延迟,还是系统容量?容量的话,SLO 定在多少、达标率多少?对比的基线是什么版本、开了哪些机制?

## 附:各论文的成绩单

这些数字来自不同负载、模型、硬件和基线配置,不能横向排名,也不能把倍数相乘。下面的“达到 X 倍”均指结果是基线的 X 倍,“多处理 X%”则指相对增量。

- **Orca**:GPT-3 175B,相同延迟水平下,吞吐最高达到论文所用 NVIDIA FasterTransformer 基线的 36.9 倍。
- **Sarathi-Serve**:对比论文中未使用 chunked prefill 的 vLLM,满足延迟 SLO 的服务容量——Mistral-7B 单张 A100 达到 2.6 倍;Yi-34B 两张 A100 最高达到 3.7 倍;Falcon-180B 配合流水线并行最高达到 5.6 倍。
- **DistServe**:在聊天场景的部分配置下,可承接请求速率最高达到 DeepSpeed-MII 的 7.4 倍;另一个 OPT-66B 摘要实验中,相较 vLLM,可把 TTFT 和 TPOT 的限制同时收紧到约 1/12.6,仍满足至少 90% 请求达标的目标。两项结果来自不同实验。
- **Mooncake**(FAST 2025 正式版):真实请求轨迹测试中,有效请求容量比比较基线增加 59%–498%;实际部署 A800/H800 集群相较之前的系统,分别多处理 115%/107% 的请求。
