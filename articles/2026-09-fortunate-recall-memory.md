# 记忆越攒越多，Agent 怎么反而越答越错

> 原文首发于微信公众号「Wenyan的呜哇」，2026-09-12。[阅读原文](https://mp.weixin.qq.com/s/A_jPquMjjRNIBsL0UTxt2w)

> 本文论文：Fortunate Recall: Ontology-Driven Memory Lifecycle Management for Persistent Coherence in LLMs ｜ Ansuman Mullick、Eray Tüzün（Bilkent 大学）｜ arXiv: 2609.10413（2026-09）｜ 代码与评测已开源（Zenodo DOI: 10.5281/zenodo.20067778）

做长期记忆的 Agent 有个共同的尴尬：记性是真好——你三年前随口说的话它都存着；但回答经常是错的——它翻出来的那条，早就过期了。

Fortunate Recall（下称 FR）把这事说透了：记忆库的问题从来不是装不下，而是没人管保质期。目前业界的记忆系统，无论商用方案还是自研框架，大多只做了两件事——"存"（全量落盘）和"压"（滚动摘要）；这篇讲的是被忽略的第三件事："管"。

## 一、核心机制：记忆的生命周期管理

FR 的思路很直接：每条事实入库时先做一次登记——由 LLM 抽出事实，并打上类目、槽位、状态、事件时间等元数据；此后这条记忆怎么衰减、何时被取代、能不能被检索到，全部由确定性规则对这组元数据打分决定，不再惊动 LLM。

先看分类。FR 把个人事实分进 10+1 个行为类目——身份、健康、爱好、义务、物流、关系、规划等等。分类依据不是"这条记忆属于什么认知类型"，而是"这类事实随时间怎么变化"——决定记忆命运的恰恰是后者。还有个细节很老练：标签打在"事实"上，而不是"原话"或"人名"上——"我改姓的时候正在办保险"，原话谈的是保险，事实属于身份。

再看四条管理规则，每条都是常识，只是第一次有人把它写成系统：

1. 各有各的遗忘速度。身份类衰得最慢，物流类最快，速率差 5.3 倍——变化速度不同，衰减参数本就不该一刀切。

2. 改地址不是加一条，是"取代"。每个"人 + 属性"是一个槽位：新事实与旧事实高置信度矛盾时，旧的不删，标记"被取代"。"考虑搬去伦敦"不取代"住在伊斯坦布尔"，"搬到了伦敦"才取代。于是问"你现在住哪"返回伦敦，问"以前是不是住过伊斯坦布尔"还能翻出旧值——记忆系统第一次有了"历史状态"。

3. 带截止日期的记忆，越近越重要。义务和物流类不按"进库多久"衰减，而按"离事件发生还有多久"激活：截止日临近活跃度上升，一过点自动失效。"按年龄衰减"在原理上就表达不了这件事。

4. 检索分诊。问身份类问题，优先在身份类目里找，而不是全库按相似度大海捞针。

LLM 只用在两处：入库时抽事实、打标签；检索时从候选里挑 top-20。中间所有生命周期判决——衰减、取代、过期、路由——是纯数学打分，中位延迟 47 微秒，每个打分项都有名字、可单独审计、用户可改参数。每轮对话总共两次 LLM 调用。

最有分量的是一个理论结果：只会"加、改、删"三种操作的记忆系统，在"过期义务"这类问题上有不可突破的错误率下限——最差情况错一半。不是模型不够聪明，是动作词表里根本没有"过期"这个词，RL 训得再努力，也学不出词汇表里没有的动作。我认为这是全文最值钱的一句诊断。

## 二、实测对比：主流记忆系统都错在哪

作者造了一个专考"时间坑"的基准 LifecycleBench：516 道题，全是改地址、过期截止日、撤回计划、多版本事实这类陷阱。参测的是工业界熟悉的记忆系统，FR-Bank 以 76.9% 居首，其余几家在 61%～70.5% 之间；在标准记忆基准 LongMemEval-S 上 FR 拿 75.2%——管好生命周期，不拖累普通检索。

比分数更有意思的是两个反直觉发现。

第一，召回率最高的系统，幻觉率也最高。A-MEM 的召回是全场冠军（87.6% Hit@5），陈旧条目也是全场冠军（30.4%），端到端幻觉率同样冠军（47%）——翻出来的陈年矛盾越多，下游模型越是一本正经地编。做检索评估的人都该记住：recall 高不等于好用，跑分里得加一列"陈旧率"。这也是不少线上系统的隐性病灶：监控看板里召回率一路走高，客诉里"AI 一本正经说错话"也一路走高——两条曲线其实是同一条。

第二，检索分数会骗人。有道题问"我之前提过又撤回了的那个计划是什么"：MemoryOS 检索通过 57%，端到端答对只有 7.5%；FR 检索通过仅 5%，端到端答对 37.5%。原因值得逐字读：MemoryOS 用摘要处理记忆，被撤回的具体计划在摘要里被洗成了"泛泛有个计划"——检索时"没看到旧答案"被判合格，但正确答案也一并没了。用压缩掩盖矛盾，等于把证据磨平。凡是用滚动摘要、滚动压缩的系统，都该对着这个案例自查一遍。

回看第一部分那个理论结果：Memory-R1 是 RL 训练的记忆管家，动作空间只有加、改、删，作者换更强模型重训后瓶颈纹丝不动——缺口在词表，不在智力。

最后贴一笔经济账：检索结果第一名是陈旧事实的占比，FR 2.1% vs Mem0 16.5%，差 8 倍；按论文的两年投影，不做生命周期管理的记忆库会攒下约 3 万条活跃边、每轮检索 top-20 里躺着 3～5 条互相矛盾的事实，做管理的只有 5～8 千条、矛盾为零；光陈旧 token 一项，按 GPT-4o 定价折算，每百万查询省约 25 美元。省的不只是钱，是"模型翻出一条旧事实、然后理直气壮编故事"的机会。

## 三、给业界的落地清单：挑最便宜的先上

完整版有六个零件（分类、槽位、状态、事件时间、路由、衰减），一次抄齐工程量不小。按收益/成本排序，我建议这样上：

1. 状态字段先行（一天）。给记忆加四个状态：在用、被取代、已过期、已撤回。先只上"取代"：识别出"更新类"事实（改地址、改偏好、改计划）时，旧值打标不删。查询时按问题意图过滤——"现在住哪"排除被取代的，"以前住哪"放行。这一步不需要分类器，规则就能起步。

2. 过期写进规则层，别让 LLM 管（半天）。带日期的事实入库时多存一个"事件时间"字段，检索前用 if 语句过滤过期项。FR 用 47 微秒干完这件事，说明它本质是查表——不要为它花一次模型调用。

3. 跑分加一列"陈旧率"（顺手）。在 precision@k / recall@k / MRR 之外，统计 top-k 里过期或被取代条目的占比。A-MEM 的教训摆在上面：召回冠军可能同时是幻觉冠军，单看 recall 会把系统引向错误方向。

4. 压缩之前，先抽"改主意"（半天）。用户说"原计划取消"后，压缩很容易把它磨平成"曾有一个计划"。摘要前先把撤回/取代事件落成状态，再让摘要只管事实内容。这一条对任何用滚动摘要的系统都成立。

## 四、局限与遗留问题

先泼冷水：10+1 类目和衰减参数是在英文个人助理场景标定的，换到别的域——代码项目的记忆、团队知识库——类目体系和速率表都要重做。论文给了标定方法，但那是一摊子活，不是改配置。摄入时的分类质量本身也只有中等可靠：作者自测的三裁判一致性 κ=0.67；低置信度矛盾时"两条都保留"的软取代只是补丁，库里照样留下"也许矛盾"的对子，靠检索时的状态过滤兜底。

第二，FR 是策略层，不是完整记忆系统，得挂在图数据库或自建存储上才跑得起来；它的工程贡献更像"一套该挂在任何记忆库外面的中间件规范"。

第三，原文没有覆盖、仍待验证的问题：中文对话里这 10+1 个类目的分类稳定性如何（中文里"身份"和"规划"的边界可能更糊）；47 微秒是 20 条候选、单线程 Python 的数字，记忆库上到百万条后路由和过滤的实际开销，原文未明说。另外它的代码和评测已开源，这点比同批许多不给代码的论文厚道。
