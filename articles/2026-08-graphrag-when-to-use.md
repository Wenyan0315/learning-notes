# ICLR 2026 论文解读：知识图谱和 RAG，什么时候用，什么时候不用

> 原文首发于微信公众号「Wenyan的呜哇」，2026-08-11。[阅读原文](https://mp.weixin.qq.com/s/dyS_K_nhYGVtj1Jyv5I0_Q)

GraphRAG 很热，但真的更好吗？

做 RAG 的人这两年应该都听过 GraphRAG。思路是先用大模型把文档抽成实体和关系，组成知识图谱，检索的时候沿着图去找上下文，而不是只靠向量相似度。

听上去挺完美的。向量检索只能找到"语义相似"的段落，图谱能把相关联的东西串起来，多跳推理、全局视野，好像把向量 RAG 的短板全补上了。

但实际用过的人会发现一个尴尬的事：不少任务里，GraphRAG 的效果反而不如最普通的 RAG，成本还高出一截。那图结构到底有没有用？什么时候有用？

ICLR 2026 收了一篇论文《When to Use Graphs in RAG》，来自厦门大学和香港理工大学的团队，就是用实验系统回答这个问题的。这篇简单讲讲。

## 他们是怎么测的

论文建了一个叫 GraphRAG-Bench 的基准，设计上有两点值得说。

第一，任务按推理复杂度分了四级：

| 级别 | 任务类型 | 例子 |
| --- | --- | --- |
| L1 | 事实检索 | 圣米歇尔山在法国哪个大区？ |
| L2 | 复杂推理 | 事件 A 和事件 B 之间有什么关联？ |
| L3 | 上下文摘要 | 综合多处信息，概括某个角色的作用 |
| L4 | 创造性生成 | 基于事实做改写创作 |

L1 考的是"找得到"，L2 往上考的是"想得明白"，需要把多个概念之间的关系串起来才行。

第二，评估是分环做的。不是只看最后答案对不对，而是拆成三段：图构建质量（实体关系抽得准不准）、检索质量（上下文相关性和证据召回率）、生成质量（准确率和忠实度）。这样结果不好的时候，能知道是哪一环拖了后腿。

测试用了英文小说和医学教材两个领域的语料，对比了几种 GraphRAG 方案和普通向量 RAG。

## 结论：两条，都不意外但终于有人测了

第一条：L1 这种简单任务上，GraphRAG 经常输给普通 RAG。

原因也好理解。事实型问题，向量检索捞一段原文基本就能答。GraphRAG 还要先认实体、再沿关系爬一圈，爬回来的邻居节点多了，真正相关的证据反而被冲淡了。图在这里带来的不是信息，是噪声。

第二条：L2 往上的复杂任务，GraphRAG 赢得比较明显。

复杂推理、跨文档摘要这类任务，缺的往往不是某个信息点，而是信息点之间的连线——答案散在好几个文档里，得顺着关系串起来才有答案。关系恰恰是图最擅长表达的东西。

所以图结构不是 RAG 的升级版，更像是 RAG 的专科医生。查个事实没必要挂专家号，多跳推理才需要会诊。这篇论文的价值，就是把"什么病挂什么号"用数据写明白了。

## 那到底什么时候该用图谱

结合论文的结论，可以粗略这么判断：

- 问题需要多跳："X 影响了哪些下游""A 和 B 怎么关联上的"，要顺着关系走两步以上，适合图谱
- 数据的价值在关系里：问答绕不开"实体之间怎么连着"，而不是"某个值是多少"，适合图谱
- 需要可追溯：结论要给出明确的关系路径，不能只是"找了几段相似的文本"，适合图谱

反过来，如果场景主要是"从一堆文档里找相似段落回答单点问题"，普通向量 RAG 就够了，上图谱纯属增加成本。

## 哪些场景其实是"立体问题"

拿搜广推和数据业务举例，这类场景里多跳问题其实到处都是：

- **指标归因：某个指标异动，想查"可能和哪次算法迭代有关"。这要把指标、数据表、算法模块、迭代记录串成一条链，单看任何一篇文档都没有答案**
- **影响面评估：改一张上游表或者一个模型特征，下游哪些指标、哪些报表会被波及。顺着依赖关系走两跳才能查全**
- **新人理解系统：一个算法的逻辑散在几十篇文档里，靠搜索逐篇翻，很难拼出全貌。如果实体和关系是连好的，"这个模块上游吃什么、下游喂谁"是一眼可查的**

这类问题的共同点是：答案不长在任何一份文档里，长在文档和文档之间的关系上。向量检索把碎片都捞出来了，但连线这件事它做不了。

## 写在最后

大模型火起来之后，知识图谱这个词显得有点像上个时代的技术。但 LLM 其实没让图谱过时，而是给它换了个位置：LLM 负责理解和生成，图谱负责提供结构化的、可追溯的关系。

向量和图谱不是谁替代谁，是分工。平面问题走向量，立体问题走图谱。选型之前，先想清楚你的问题是平的还是立体的。
