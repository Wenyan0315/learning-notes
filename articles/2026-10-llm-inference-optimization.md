# 大模型为什么一个字一个字地"蹦"？四篇论文讲清推理加速

> 原文首发于微信公众号「Wenyan的呜哇」，2026-10-10。[阅读原文](https://mp.weixin.qq.com/s/l7dvWFgir6Hg--7bw2byTA)

你可能遇到过这样的情况：向 AI 发出问题，先等上几秒，回答才开始出现；随后，文字又像挤牙膏一样慢慢往外冒。

这两种"慢"，原因往往不同。

前一种，可能是模型正在处理你发过去的长文，也可能是请求还在排队。后一种，则与模型生成回答的方式有关：它通常要一步接一步地预测下一小段文字。

但速度并不只由模型大小决定。同一个模型，运行它的软件系统不同，服务效率也能相差很大。

为什么？下面用四篇代表性论文，串起一条理解大模型推理优化的主线：少搬数据、提高利用率、少做重复工作。

## 01｜模型回答你，其实分两步

先说清"推理"：训练是在调整模型参数，推理则是用训练好的参数处理输入、生成结果。本文讨论的是常见的自回归 Transformer 大模型。

模型处理文字的基本单位叫 token，可以把它理解成文字片段。它可能是一个汉字，也可能是一个词的一部分，因此"一秒多少 token"并不等于"一秒多少字"。

一次回答通常分成两个阶段。

第一步，处理问题，叫 Prefill。

你把问题、聊天记录，甚至整篇文档交给模型。模型在因果注意力的约束下，并行处理这些输入位置，算出后续生成需要的中间结果。

第二步，继续生成，叫 Decode。

模型预测下一个 token，把它接到已有内容后面，再预测下一个。如此循环，直到回答结束。

这就像先读题，再落笔。但这个比喻只帮助理解流程，并不意味着模型像人一样阅读和思考。

为了避免每写一步都把前文重新计算一遍，系统会保存注意力计算中的 Key 和 Value，简称 KV cache。

可以把它当成模型给前文留下的"计算笔记"。后续生成直接读取这些笔记，省下重复计算。代价是：笔记要占显存，而且随着上下文增长不断变大。

用户关心的速度，也要分开看：

- 多久开始回答：首 token 延迟，包含排队、输入处理等时间。
- 回答出现得有多快：生成阶段每个 token 的平均耗时。
- 能同时服务多少人：系统吞吐量，通常用每秒处理的请求数或 token 数衡量。

能同时接待更多用户，不代表每位用户都能更快拿到回答。这点很重要：后面论文里的"加速"，有的说的是延迟，有的说的是吞吐量。

## 02｜GPU 很能算，为什么还会慢？

想象一家厨房：厨师负责计算，仓库负责存数据。

厨房效率既取决于厨师切菜有多快，也取决于食材能否及时送到案板上。厨师再多，如果一直在等食材，也忙不起来。

GPU 同样如此。它有容量较大的高带宽显存，也有容量较小、访问更快的片上存储。计算需要不断读取模型权重和中间结果，数据搬运也要花时间。

在输入较长、计算规模足够大时，Prefill 往往能组织出较大的矩阵运算，更容易充分利用 GPU 算力。

而在低并发、逐 token 生成时，每一步虽然只生成很少内容，却仍需读取大量权重和 KV cache，Decode 往往更容易受显存带宽限制。

这里的关键词是"往往"。批量大小、上下文长度、模型结构和硬件配置都会改变瓶颈；长上下文的注意力计算本身，也可能受到访存限制。

不过，"厨房"这个视角仍然很有用。理解推理加速，可以先问三个问题：

能不能少搬一些数据？一次搬运能不能支持更多工作？已经做过的工作能不能复用？

四篇论文，分别从不同位置回答了这些问题。

## 03｜FlashAttention：别把中间结果搬来搬去

注意力机制让模型根据上下文，决定哪些信息更值得关注。

传统实现往往会显式生成很大的注意力中间矩阵。序列越长，这些矩阵越大；其中一些还要被写回显存，再被后续步骤读出来。

好比厨师切好一盘菜，先送回仓库，下一道工序又去仓库把它取回来。操作没错，但来回搬运很费时间。

2022 年的 FlashAttention 换了一种计算安排：把数据切成适合片上存储的小块，逐块处理，并利用在线 softmax 更新归一化结果，避免把完整的注意力中间矩阵写入显存。[1]

它的关键不是把标准注意力换成近似算法，而是保留注意力的数学计算，减少中间数据的显存读写。

这也不意味着注意力的计算量从此不再随序列长度平方增长。它主要改善的是数据搬运和中间存储，而非消除所有平方级计算。

对推理而言，这个思路在长输入的 Prefill 中尤其值得理解。它也广泛用于训练；原论文中的训练加速数字，不能直接当作聊天生成速度的提升。

记住一句话：算得一样，安排不同，也可能快很多。

## 04｜PagedAttention：把显存用好，才能同时接更多请求

FlashAttention 优化一次计算内部的数据流。到了推理服务层面，还有另一个问题：显存能容纳多少个正在生成的请求？

麻烦就在 KV cache。

回答没结束之前，系统很难知道它最终会有多长。如果提前为请求留出很大的连续空间，可能浪费；如果剩余空间零散，又可能明明还有空位，却放不下新请求。

2023 年的 PagedAttention 借用了操作系统管理虚拟内存的思路：把 KV cache 分成固定大小的块，通过块表记录它们的位置。[2]

逻辑上连续的上下文，物理上可以放在不同显存块里。需要更多空间时再分配，请求结束后再回收。最后一个未填满的块仍可能有少量浪费，但不必再按最大长度预留整段空间。

这像把仓库从"一位顾客包下一整排货架"，改成"需要多少，分配多少格"。

省下显存之后，系统就有机会把更多请求组成一个批次，也就是 batch。多个请求共同运行时，一次权重读取可以支持更多计算，提高 GPU 利用率。

承载这项技术的系统叫 vLLM。它还结合了持续批处理：完成的请求退出，新请求动态加入。持续批处理是相关的调度机制，并不是分页本身发明出来的。

论文报告，在其评测条件下，vLLM 相比 FasterTransformer、Orca 等系统，在相近延迟水平下实现了约 2—4 倍吞吐提升。[2] 这是整套系统的效果，不能全部归到一个机制上，也不等于每位用户的生成速度都翻了几倍。

记住一句话：显存少浪费，服务才能装下更多工作。

## 05｜投机解码：小模型打草稿，大模型批改

即使显存管理得很好，逐 token 生成仍然有串行依赖：下一步要接着前一步的结果继续。

Speculative Decoding，投机解码，尝试减少大模型必须串行运行的轮数。[3]

做法很直观：先让一个成本较低的小模型起草几个 token，再交给大模型一次性验证。

为什么验证可以并行？因为待检查的整段草稿已经给出，大模型可以在因果注意力下，同时计算各位置对应的条件概率。它不用先完成"采样出前一个 token"这件事，才开始计算后一个位置。

但草稿终究可能写错。算法会从前往后决定接受哪些 token；遇到拒绝的位置，就按专门的修正分布重新采样，后面的草稿也随之作废。

精妙之处在于：在论文规定的接受和修正规则下，最终采样分布与直接使用目标大模型一致。

这里说的是概率分布一致，不是任意两次运行都会逐字输出同一篇回答；随机采样本来就可能产生不同结果。

原论文在 T5-XXL 的实验中报告了约 2—3 倍加速。[3] 这个数字也不是普遍保证：草稿质量、起草成本、验证开销和批量大小，都会影响实际收益。

草稿经常被接受，就能减少大模型的串行轮数；如果总被打回，起草反而可能成为额外负担。

记住一句话：多做一点便宜的预测，换取少跑几轮昂贵的大模型。

## 06｜RadixAttention：相同的开头，别反复读

前面讲的是如何高效计算。还有一种更直接的提速：有些计算已经做过，能不能别再做？

例如，一个客服系统的所有请求，都以同一段很长的系统提示开头；多轮对话每次调用，又会带上前面的历史记录。

只要前缀相同，并满足相同模型、位置与相关配置等复用条件，这部分 KV cache 就有机会被再次使用。

SGLang 论文中的 RadixAttention 用基数树组织这些前缀及其缓存，让系统自动匹配、保留和复用已有结果。[4]

可以把它理解为一本会分叉的目录：

> 请求 A：共同说明 → 问题 A
>
> 请求 B：共同说明 → 问题 B
>
> 请求 C：共同说明 → 问题 A → 追问

共同的开头只需保留一份计算结果。后面的内容不同，就沿着不同分支继续处理。

这里有一个容易误解的边界：复用依赖相同前缀，不是看到任意位置有一段相同文字就能复用。

同一份文档，如果前面的问题不同，其对应的 KV 也可能不同，因为这些表示受到前文影响。文本相同，不足以保证计算结果相同。

PagedAttention 也支持 KV 共享。两者可以配合：分页侧重缓存如何分配和存放，RadixAttention 侧重哪些已有前缀能被发现并再次利用。

这种优化的收益取决于实际请求：重复前缀越多、缓存越容易命中，收益通常越明显；请求几乎没有共同开头时，能省下的工作就少。

SGLang 还有结构化输出等优化，论文中的整体加速不能全部算在 RadixAttention 头上。为了把主线讲清楚，这里先聚焦前缀复用。

记住一句话：重复出现的前缀，可以复用它的计算笔记。

## 07｜四种加速，分别省了什么？

把它们放在一起，会发现它们并不互相替代：

- FlashAttention：减少注意力计算中的中间数据搬运。
- PagedAttention：减少 KV cache 的空间浪费，为更有效的批处理创造条件。
- 投机解码：通过起草和验证，减少目标模型的串行生成轮数。
- RadixAttention：复用相同前缀的 KV cache，减少重复输入处理。

一套推理系统可以组合使用这些思路，但加速倍数不能直接相乘。某处瓶颈缓解之后，新的瓶颈可能出现在计算、访存、通信或调度上。

这些工作也说明：让大模型更快，不一定要先让它变小。计算怎样安排、显存怎样管理、结果怎样复用，同样重要。

FlashAttention 做的是精确注意力，但浮点运算顺序改变后，数值结果不保证逐位相同；投机解码的同分布结论依赖正确的采样规则；缓存复用也有前提。理解这些条件，比记住一个漂亮的加速倍数更有价值。

以后再看到"某项技术让大模型快了几倍"，可以先问：

它让开始回答更快，还是后续生成更快，或者只是能同时服务更多人？测试用了什么模型、硬件和负载？它到底省掉了哪一部分工作？

问清这几件事，推理优化就不再是一串难记的技术名词，而是一笔能看懂的计算账。
